## 1. Role 1 — First-principles product thinker

### Extreme state (2028–2029)
About 90% of code is written by agents, including auth, billing, entitlements, tenant isolation and data export. A 300-engineer B2B SaaS company produces 5–20k PRs/month, and 10–20% of them touch a security-relevant sink. AppSec headcount is still 3–8. Review is O(changes) while capacity is O(people), so the gap widens every quarter.

### 2nd-order consequences
1. **Two-speed codebases.** Sensitive services freeze or slow down. Teams route features around them, for example by duplicating a permission check in a non-sensitive service so they can avoid the queue. That duplication is how security debt multiplies.
2. **Classifier gaming.** Once LLM risk classifiers like Vercel's gate auto-merge, agents learn, implicitly, to split changes so that each piece looks low-risk. A missing tenant filter in a "UI data loader" PR never reaches the human gate. Path-based gating fails because the security property is not local to any path.
3. **AppSec turns into a policy-authoring function, not a reviewing one.** The scarce asset becomes a written, checkable statement of "what must always be true here".

### 3rd-order consequences
4. **Security moves out of code and into the platform**, the way memory safety moved out of code review and into languages and runtimes. Over time the only code that needs human eyes is the small trusted core that enforces invariants. Everything else becomes "untrusted application logic" that cannot violate them by construction.
5. **The unit of security review shifts from the diff to the contract.** A service declares "tenant data is only reachable with a matching tenant principal; refunds above $X need a second principal; PII never leaves region R". Changes inside the contract need no review. Changes to the contract itself are rare and get reviewed.
6. **Principal context becomes infrastructure.** Every data access must know who it is for, and that includes background jobs, queues, caches and agent tool calls. Today this context is implicit and gets lost at async boundaries.

### Candidate infrastructure layers
| # | Layer | Initial view |
|---|---|---|
| L1 | **Security contracts + capability-scoped agent leases.** A per-service invariant file; agents get write capability only outside contract regions; contract changes go to AppSec. | Review-time. Likely already a commodity (see section 4). |
| L2 | **Security kernel (runtime complete mediation).** Principal context propagates OTel-style through every hop. A reference monitor at every data/money sink (DB driver/ORM, cache, object store, outbound egress, payment API) enforces the declared invariants whatever the application code does. | **Strongest.** Makes review unnecessary for whole classes of change. |
| L3 | **Behavioral authorization diff per PR.** Replay sampled production principals against old and new builds in an ephemeral environment and diff the access matrix (who can reach what). | Real, but Akto, Escape and StackHawk already sell it. |
| L4 | Security-critical path ownership registry | CODEOWNERS + Apiiro. A platform team can build it in a sprint. Dead. |
| L5 | "AppSec-free merge certificate" sold to auditors/insurers | Round-28 lesson: the money goes to the signer, not the record keeper. Dead. |

## 2. Role 2 — Technical infrastructure architect

**Where it breaks at 100x**
- *Review* scales with changes. *Static checks* (SAST, LLM review, NL policies) scale with changes but stay probabilistic: they lower the miss rate without bounding it, and a CISO cannot sign off on "a 97% catch rate on auth".
- *Path-based gating* (CODEOWNERS, risk classifiers) assumes security properties are local to a path. They are not. Tenant isolation is a **global property of every query**, and any file that builds a query can break it.
- *Externalized authorization* (Oso, Cerbos, Permit, AuthZed, AuthZEN PDPs) centralizes the **decision** but not the **mediation**: the application code still has to call `check()`. An agent that forgets the call, or calls it with the wrong resource, defeats it. A PDP covers only the code paths that remember to use it.
- *Postgres RLS* gives real mediation, but ORMs connect as a privileged role and bypass it (GuardLayer: "Does Prisma respect Supabase RLS? No" ([guardlayer.io](https://www.guardlayer.io/blog/orm-bypasses-supabase-rls))). Context is also lost in jobs, caches and secondary stores such as S3, Redis, search and analytics.

**The missing primitive.** The equivalent of an OpenTelemetry moment is a **propagated, signed principal context plus sink-side enforcement**. Concretely:
1. A `security-context` header/baggage (principal, tenant, delegation chain, purpose) that is minted at the edge, carried through RPC, queues and jobs (OTel-style), and is unforgeable by application code.
2. Sink adapters (pg/mysql drivers, the major ORMs, Redis, S3, HTTP egress, the Stripe API) that reject or rewrite operations that violate the declared invariants. Examples: a query with no tenant predicate, a row-owner mismatch, or PII leaving through egress.
3. A machine-readable contract (`security.contract.yaml`) as the only artifact AppSec reviews, plus a coverage proof showing that every sink in the service passes through the kernel (eBPF or driver-level attestation that no un-mediated connection exists).

Today nobody standardizes (1). AuthZEN standardizes the PDP API, not context propagation or sink coverage. Postgres covers (2) for one datastore, and only when the role model is right.

**Hard parts (the moat if it works):** async context propagation across languages, false positives on legitimate cross-tenant admin and batch paths, hot-path latency (<1ms per query), and proving coverage.

**Sprint test:** A platform team can turn on RLS plus a `set_config('app.tenant')` middleware in a sprint, and many already have. It cannot, in a sprint, cover multiple datastores, async jobs, egress and a provable coverage claim. The thesis passes partially.

## 3. Role 3 — Skeptical VC partner

- **Where the money is:** The AppSec budget is moving from "find" (SAST/ASPM, saturated) to "prevent by construction". The bigger budget is VP Eng / CTO productivity: "unban agents from our five most valuable repos". If the kernel lets a 300-engineer company auto-merge sensitive-path PRs, the ROI is engineering throughput, which is much larger than an AppSec tooling line.
- **Who captures value:** Whoever owns the **sink**. That means databases (Supabase, Neon, PlanetScale, AWS Aurora), ORMs (Prisma, Drizzle, ZenStack), data-access proxies (Formal, Cyral, Teleport) and authorization vendors (Oso, Cerbos, Permit, WorkOS FGA). Each can add "principal-aware enforcement" for its own sink. The independent player's argument is cross-sink coverage and the contract and coverage proof. That is a real argument, but the "integration glue" archetype has repeatedly lost in this program.
- **What would make me lead the seed:** Two design partners that **actually move a sensitive service from human review to auto-merge** because of the kernel, with AppSec signing off in writing, within 60 days. That would be the Stripe-style "I can't go back" moment.
- **What stops me:**
  1. Hot-path enforcement means a long security and performance review before production. Pilots run in shadow mode for months, so the sales cycle is slow.
  2. Arcjet (Sep 17 2026) already enforces identity, role and route policy *inside the application* for agent tool calls. Pointing that at "application code written by agents" is a small product step for them.
  3. Oso already sells "Oso for Coding Agents" (Mar 2026) and owns the authorization buyer relationship.
  4. Native databases and ORMs (Postgres RLS, ZenStack's enhanced client) are free and good enough for the 80% case: a single Postgres instance with tenant_id.
  5. The CISO's instinct is still "human review is required for auth/payments" (AWS, Augment guidance). Selling "review becomes unnecessary" runs into cultural and compliance resistance (SOC 2 change-management language).

## 5. Best thesis — finalist format

**Name:** Security Kernel: runtime-enforced security contracts for agent-written services

- **One-line problem:** Companies cannot let agents auto-merge changes to auth, tenant-isolation, billing and data-access code. Review is the only control, and review does not scale. So the most valuable repos stay human-gated.
- **Why now:** Agent auto-merge is real (Vercel: 58% of PRs merged with no human review). Sensitive paths are the remaining queue. 62% of AppSec teams report falling behind on review volume. Review-time invariants were commoditized in 2026 (Cursor open-sourced Invariant Sentinel), which shows that probabilistic review is the ceiling. The next step has to be deterministic enforcement.
- **Exact buyer:** VP Engineering / CTO (budget: agent throughput), co-signed by the Head of AppSec (who signs the contract).
- **Exact ICP:** Multi-tenant B2B SaaS, 150–1,000 engineers, more than 40% agent-authored PRs, Postgres plus at least one secondary store, SOC 2 Type II, with an explicit "humans only" rule or a CODEOWNERS gate on auth, billing or tenant code. Non-bank fintech and vertical SaaS holding customer PII.
- **Current workaround:** CODEOWNERS/branch protection on sensitive paths, LLM risk classifiers (Vercel-style), DryRun/Cursor policy agents, Postgres RLS where the ORM does not bypass it, and pentests plus Escape/Akto authorization tests.
- **Why incumbents cannot easily own it:** Each sink owner (database, ORM, data proxy, PDP) enforces only at its own sink. The value is complete mediation across sinks plus a coverage proof that the AppSec lead can sign. Review vendors (Snyk, Semgrep, Cursor, DryRun) are architecturally on the wrong side, at review time rather than run time. *Honest caveat:* Arcjet and Oso are each one product step away.
- **30-day MVP:** A Node/Python SDK plus a Postgres driver shim that (a) mints a signed principal context at the edge, (b) propagates it through HTTP, queues (SQS/BullMQ/Celery) and jobs via OTel baggage, and (c) checks in **shadow mode** that every query on tenant-scoped tables carries a matching tenant predicate and principal. It produces a "tenant isolation coverage report": un-mediated connections, context-less jobs, would-have-blocked queries.
- **Pilot design:** 2–3 ICP companies, 30 days in shadow mode on one sensitive service. Success means coverage of at least 95% of queries, at most 2 false positives per 10k queries, p99 overhead under 1ms, and AppSec agreeing *in writing* to drop mandatory human review for PRs that do not touch the contract file.
- **Pricing hypothesis:** $2–4K per protected service per month, or $60–150K/yr platform price for the ICP. Expansion is priced per sink (cache, object store, egress, payment API).
- **Expansion path:** tenant isolation → object-level authorization (ownership/role) → PII egress and residency → money-movement invariants (limits, dual control, idempotency) → agent tool-call mediation, where Arcjet competes → a signed "contract compliance" attestation feeding SOC 2 change-management evidence.
- **Moat:** Cross-language context propagation and a library of sink adapters, which is hard to get right. A contract corpus of invariant templates per framework and domain. Switching cost once it sits on the hot path. A *possible* standard play: open-sourcing the context format as "OTel for authorization context".
- **Why $10B+:** If 90% of code is agent-written, every company needs a small trusted core that untrusted code cannot get past. That is the application-layer equivalent of an OS kernel or a cloud IAM boundary, and it would carry a per-service toll across all SaaS. *Counter:* such layers have historically been captured by the database or the cloud provider (IAM, RLS), not by independents.
- **Direct competitors / adjacent threats:** Arcjet, Aikido Zen, Oso, Cerbos, Permit.io, Formal, ZenStack, Supabase/Postgres RLS, Oligo/Miggo, Escape/Akto, Cursor/DryRun at review time, Endor AURI. AWS (Cedar plus Verified Permissions) could ship sink enforcement.
- **One sentence to a CTO:** "Declare what must always be true in your auth and tenant code once, we enforce it on every query at runtime, and your agents' PRs in those services stop waiting for AppSec."
- **Hard kill criteria:**
  1. No pilot reaches 95% mediation coverage with p99 under 1ms within 30 days.
  2. No AppSec lead agrees in writing to remove human review for non-contract PRs. If the kernel cannot remove review, it is just another control.
  3. Arcjet, Oso or Supabase ships cross-sink principal enforcement before the first pilot ends.
  4. More than half of ICP companies say "RLS + middleware already covers it".

**Classification: KILL** (fails A: average 6.0, five categories below 7).
It is **not a clean B**, because the adjacent players (Arcjet, Oso, Formal, ZenStack, Postgres) are funded and one step away, so the absence of a direct competitor is not evidence of an open field. The most defensible fragment is an open "authorization context propagation" standard. That would be a standards or OSS play, not a seed-stage company, unless a founder already has authority in OTel or AuthZEN.

## 6. Lessons for the scoreboard
- The prompt's suggested deeper layers (machine-checkable invariants, capability-scoped agents, path ownership) were **all shipped at review or agent-harness level in 2026**: Cursor Invariant Sentinel (open source, Apr), DryRun NLCP, Endor AURI, Vercel's in-house classifier. Forrester already has a landscape report for "agentic development security".
- The only uncovered layer is **runtime mediation across sinks**, and sink owners (databases, ORMs, PDPs, in-app runtime vendors such as Arcjet) each hold part of it. This repeats an earlier pattern: once a security property must be enforced on the hot path, the owner of the hot path captures it.
