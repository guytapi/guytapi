## Role 1 — First-principles product thinker

### Extreme future (2028-2029)
A company with 2,000 engineers runs about 5-20k agent instances: coding agents in every repo, plus background, review, ops and business-process agents. Each one's behavior comes from a stack of 6-8 config layers, each with a different owner:
1. Vendor defaults and the model.
2. Enterprise managed policy (security).
3. Org-level custom agents, skills and plugins (platform).
4. Team skills and MCP allowlists.
5. Repo AGENTS.md / CLAUDE.md / rules.
6. User settings.
7. Runtime-injected context (memory, tool descriptions from third-party MCP servers).

No single person can see the "effective config" of any one run.

### 2nd/3rd-order consequences
1. **Config changes become behavior changes with a blast radius but no release process.** A one-line edit to a shared skill or an org deny rule silently changes thousands of agent runs. Evidence that this already happens: arXiv 2608.23067 found that injecting skills *reduced* Pass@2 by 1.3-4.2% and raised token cost by 72-394%, with gains in only 17-36% of skill-project pairs. Config can quietly make agents worse.
2. **Composition conflicts across owners.** Security's deny rule breaks a team's skill. Repo instructions contradict org instructions. Different vendors read different files (Nerviq: "most repos score 10-20/100"; Claude, Cursor and Copilot configs contradict each other).
3. **Config becomes a supply chain.** Studies of 10,008 public repos (paper surfaced via agentpatterns.ai and emergentmind) found:
   - 10.1% of agent config paths are exact SHA-256 duplicates across independent repos.
   - 58% have a single-commit history.
   - Almost none declare permission boundaries.
4. **Model upgrades invalidate config.** Instructions tuned for model N regress on model N+1, which forces fleet-wide retuning on every model release.
5. **Third order:** "agent behavior owner" becomes a role, much as SRE did. Config turns into the actual operating policy of the company, and auditors and insurers eventually ask "what policy was this agent running when it did X?"

### Candidate infrastructure layers
- **L1. Agent Behavior Release Control** (the best candidate). Every change to any shared config layer gets four things:
  - Computed blast radius: which repos, agents and runs inherit it.
  - Replay of sampled real past tasks under old and new config, producing a behavioral diff.
  - Ring rollout across repos/teams.
  - Automatic rollback on outcome metrics (merge rate, CI pass, revert rate, cost).

  "Argo Rollouts for agent behavior", cross-vendor.
- **L2. Policy compiler.** You write org intent once ("payments repos: no prod creds, Opus only, these 4 MCP servers, human approval on migrations"). It compiles to each vendor's native settings (Claude managed-settings.json, Codex requirements.toml, Cursor team rules, Copilot custom agents, Agentforce topics) and verifies the effective config that actually ran.
- **L3. Config attribution telemetry.** Which instruction, skill or tool each run actually used, and its outcome. This finds dead config, harmful config, and "which line caused this incident".

## Role 2 — Technical infrastructure architect

**What breaks at 100x:**
- Git-based distribution (central repo → sync bot → PRs to N repos) works at 50 repos and fails at 5,000. Sync PRs pile up unmerged, and every repo forks locally.
- Precedence rules differ per vendor, so the effective config can't be known without simulating each harness.
- There is no causal link between a config version and an outcome: OTel GenAI spans record model and prompt, not "skill X v3 from layer 4".

**The missing primitive (Kafka/OTel moment).** A content-addressed **effective-config manifest per agent run**: hashes of every layer plus resolved precedence, emitted as a standard span attribute. Release control (L1), attribution (L3) and audit all depend on it. It is truly missing as a standard.

It is likely to be absorbed, though:
- APM already produces lockfiles with content hashes.
- Vendors control the harness and can emit the manifest natively in a quarter.
- GitHub's agent control plane already logs sessions per custom agent.

**Can a platform team build it in a sprint?**
- L2 compile-to-native for 3 vendors: yes (a templating job plus MDM push).
- L3 attribution on top of vendor OTel: mostly yes.
- L1 replay: no. Sandboxed, repeatable replay of real tasks across repos is weeks to months of work, but Faros sells exactly this.

## Role 3 — Skeptical VC partner

**Where is the money?**
- Coding-agent seats run about $40-200 per developer per month. Config management sits at 5-10% of that at best, so roughly $3-15 per developer per month.
- A 2,000-engineer company would pay $70-350K/yr. That is a real but feature-sized budget, owned by the DevEx lead and not the CISO.

**Who captures value?**
- Distribution and enforcement go to vendors, who own the file formats and the harness: Anthropic managed settings; GitHub enterprise AI controls (GA Feb 2026, org custom agents Aug 2026); Cursor team rules.
- Free cross-vendor packaging goes to Microsoft APM and AgentRC.
- Outcome measurement goes to engineering-intelligence vendors that already have the telemetry and buyer (Faros, DX, Jellyfish).
- Production (non-coding) agent rollout goes to LaunchDarkly AgentControl (launched May 19, 2026): central config, benchmark before rollout, controlled rollouts, sub-200ms runtime changes.

**What would make me lead the seed:**
- Evidence that cross-vendor heterogeneity persists (companies standardize on 2-3 harnesses, not 1).
- A shared config change causing a measured incident at 3+ companies.
- Replay that is 10x cheaper or more faithful than Faros's.

**What stops me:**
- Every layer has a funded owner or a free Microsoft tool.
- The buyer is a DevEx lead with a tooling budget.
- The moat is a corpus of replay results, which vendors (who have far more traces) can copy.

## Finalist format — L1 "Agent Behavior Release Control" (written up to document the kill)

- **One-line problem:** One edit to a shared skill, org policy or default model silently changes the behavior of thousands of agent runs across hundreds of repos, with no blast-radius view, no canary and no rollback.
- **Why now:** Org-level custom agents and skills went GA in 2026 (GitHub Aug 2026; Anthropic org skills and managed settings). Skills can measurably hurt (arXiv 2608.23067). 58% of configs are written once and never revised. Model churn arrives quarterly.
- **Exact buyer:** Head of Developer Platform / AI Enablement.
- **Exact ICP:** 500-5,000 engineers, 300+ repos, 2+ coding-agent vendors, a central "agent standards" repo already in place.
- **Current workaround:** A central standards repo with a sync bot (agentpatterns.ai's "canary repos first, then wider" pattern), CI drift checks, AgentRC/Nerviq audits, manual spot checks, and Faros for outcome dashboards.
- **Why incumbents can't easily own it:** Weak argument. A single vendor can't see the other vendors' agents, but APM (cross-vendor) and Faros (cross-vendor outcomes) already sit in neutral positions.
- **30-day MVP:**
  - A GitHub App that resolves effective config per repo for Claude, Codex, Cursor and Copilot.
  - For a proposed change to a shared layer: list affected repos, replay 30 merged PRs per ring in sandboxes under old vs new config, report the diff in pass rate, cost and tool calls.
  - Gate the merge on the result.
- **Pilot design:** 2 design partners, 3 historical config changes each, replayed. Pass if at least one silent regression per partner was missed by their existing process.
- **Pricing hypothesis:** $8/active developer/month, or $50-150K/yr platform fee.
- **Expansion path:** Policy compiler (L2), then attribution telemetry (L3), then non-coding agent fleets, then a compliance record of "policy in force per action".
- **Moat:** A cross-company corpus of config-change → outcome results ("this kind of instruction hurts model X"). Weak, because vendors see more traces.
- **Why $10B+:** Only if agent config becomes the company's operating policy for tens of thousands of agents across vendors and the release-control layer becomes the system of record for it, as Kubernetes plus Argo did for workloads. Current evidence doesn't support neutral capture.
- **Competitors & adjacent threats:** Faros AI, LaunchDarkly AgentControl, Microsoft APM + AgentRC, GitHub agent control plane, Anthropic managed settings, Tessl, Runtime (YC P26), Caliber, Nerviq, Datadog/Braintrust replay, DX/Jellyfish.
- **CTO sentence:** "Last month your platform team changed one shared skill and it went to 400 repos. Do you know whether agents got better or worse?"
- **Hard kill criteria:**
  1. Design partners' config changes show <1 measurable regression per quarter.
  2. Partners run a single vendor, so native tools suffice.
  3. Faros, GitHub or Anthropic ships ring rollout with replay within 2 quarters.
  4. Replay costs more than $5K per change at partner scale.

### Other candidates (scan-level)
- **L2 policy compiler across vendors:** 4.8. Buildable in a sprint (template plus MDM push); APM and vendor managed settings cover it.
- **L3 config attribution telemetry:** 5.0. A feature of Faros, DX or Datadog; vendors will emit the manifest natively.
- **B-check: non-coding enterprise agent fleets** ("policy compiled per business agent" across Agentforce, Copilot Studio, ServiceNow, internal agents): pre-demand for multi-vendor fleets. LaunchDarkly AgentControl, Microsoft Agent 365 and ServiceNow AI Control Tower already claim the control plane. Not B.

### Lesson
The H8 decoy ran deeper than the brief assumed. Behind skills registries and MCP gateways, every follow-on layer was taken by Oct 2026:
- Packaging: APM.
- Lint and eval: AgentRC, Nerviq.
- Runtime canary: LaunchDarkly.
- Replay and outcomes: Faros.

Microsoft shipping two free cross-vendor tools (APM, AgentRC) shows the platform owners treat agent config as an open standard to give away, not a layer to sell.
